# S12 Piper 固件兼容性与软件路线

## 当前结论

左臂 J2 的 `+0.005 rad`、5% 位置-速度指令曾导致 J2 相对基准超过 `0.020 rad`，同步高速
反馈显示 J2 与 J3 电机均实际运动。ROS/CAN 基准最大差只有 `0.000263 rad`，CAN 无总线错误，
因此目前不能用采样时差、单帧噪声或 CAN 故障解释该现象。AGILEX 当前
[PIPER 产品使用资料清单](https://agilexsupport.yuque.com/staff-hso6mo/alxgtf/gg11q9ywverdd8rk?singleDoc#)
明确将低于 `S-V1.8-8`（不含 `S-V1.8-8`）的机械臂导向 `piper_sdk` 与
`piper_ros/noetic`；左右 `S-V1.8-2` 属于该范围，当前固定软件路线因此通过版本矩阵检查。
这项兼容性结论不解释已经观测到的异常运动，S12 仍因真机事件保持阻塞。

固定运行版本为：

- `agilexrobotics/piper_ros@ac41fcbcdda598f01b51cf6175ed9a24d0dacadc`
- `agilexrobotics/piper_sdk@081e7c588e5b79eeaefa67a0469bcc701c81014f`（0.6.1）
- 左右 Piper 实机固件均为 `S-V1.8-2`（2026-09-14 通过 SDK 查询取得）
- Ubuntu 20.04、ROS Noetic、Python 3.8、SocketCAN 1 Mbps

不要在厂商问题单中填写机械臂序列号、资产编号、人员、站点或网络标识。

## 官方资料约束

厂商 2026-07 资料清单（页面于 2026-09-01 更新）把二次开发入口分成两条路线：`pyAgxArm`
和 `agx_arm_ros` 标为兼容所有固件；旧 `piper_sdk` 和 `piper_ros/noetic` 仅用于低于
`S-V1.8-8` 的固件，不包含 `S-V1.8-8`。本项目不在 S12 迁移控制栈，继续固定后一条路线。

官方 Piper ROS 文档按固件 `S-V1.6-3` 分隔 URDF：此前使用旧模型，此后 J2/J3 坐标系偏移
2°并使用当前模型。左右实机均为 `S-V1.8-2`，因此不属于旧 URDF 范围，当前模型选择与
该官方分界一致。固定 SDK 说明 0.0.x 用于 `V1.5-2` 以前的固件；这只排除了旧固件专用
SDK 路径，尚不能证明 0.6.1 对本次 J2/J3 运动现象的兼容性。

官方双臂说明还区分主臂和从臂：主臂发送 `0x151`、`0x155`–`0x157` 等控制帧；控制从臂时
不得让另一个主臂通过航空插头持续发送控制。现场必须确认两台 Piper 的角色和物理接线，
不能把 Pika USB 串口身份当作该项确认。

2026-06-22，AGILEX 官方 `pyAgxArm` 仓库维护者在
[Discussion #58](https://github.com/agilexrobotics/pyAgxArm/discussions/58) 中确认
`S-V1.8-2` 的 Leader/Follower 状态复发、零点/参考重建和限位参数损坏属于已知固件缺陷，
并指定 `S-V1.8-9` 为永久修复版本。相关
[piper_sdk issue #114](https://github.com/agilexrobotics/piper_sdk/issues/114) 记录了
MOVE J/MIT 模式切换后零点或参考重建。该证据与本项目现象相关，但不能据此断言两者具有
完全相同的触发路径，也不能推翻当前资料清单对软件路线的明确分配。因此这些记录作为运行
风险和诊断约束保留，不再被解释为“`S-V1.8-2` 一律禁止使用”。

官方 `piper_sdk` 0.6.2 相比 0.6.1 主要分离 Linux CAN 收发 bus，以减少资源竞争造成的
延迟或发送失败；其发布说明没有声称修复 `S-V1.8-2` 固件问题。因此当前不以单独升级 SDK
替代固件修复，也不在存在安全异常时通过试运行比较 SDK 版本。

## 固件采集

固件版本不能从普通被动反馈帧可靠取得。官方 SDK 的 `ConnectPort()` 默认执行 `PiperInit()`，
会发送 `0x472` 限位查询和 `0x4AF` 固件查询；它不是纯接收操作。项目入口明确区分检查和执行：

```bash
scripts/query_piper_firmware.sh check left
scripts/query_piper_firmware.sh check right
```

上述 `check` 只验证 CAN 身份并打印计划，不发送帧。现场确认机械臂保持禁用、没有 ROS master
或驱动进程后，才可分别执行：

```bash
scripts/query_piper_firmware.sh apply left --confirm-query-only
scripts/query_piper_firmware.sh apply right --confirm-query-only
```

`apply` 不调用使能、模式、关节、夹爪、reset 或 stop API，只打印完整的八字符 `S-V...`
固件版本。2026-09-14 左右查询均返回 `S-V1.8-2`，结果已填入 Git 忽略的
`config/s07-hardware.env`，未写入示例文件。左臂首次读取曾只收到中间态 `S-V1`；脚本已
改为拒绝未收完整的响应并重查成功，避免把协议分段到达误记成固件版本。

## 当前版本决策与门禁

设备负责人已决定不升级固件。本阶段保持 `S-V1.8-2`，不自动下载或刷写固件，也不迁移到
`pyAgxArm`。低速验收工具在使能或运动前读取 Git 忽略的本机固件记录，只接受本项目已经
审查的旧栈范围 `S-V1.8-0` 至 `S-V1.8-7`；从 `S-V1.8-8` 起必须先切换并审查厂商指定的
新软件路线。缺失或格式不完整的记录仍会在访问 ROS master 前失败。

版本矩阵门禁通过不构成运动授权。再次使能或运动仍必须先关闭本次 J2/J3 异常事件，核验
当前模式、主从角色以及固件关节参数，并满足 `config/s12-acceptance.env` 的独立现场门禁。
在取得充分证据前，不进行 MOVE J/MIT 模式切换、零点重建、参数写入或新的运动尝试。

关节参数使用 `scripts/query_piper_limits.sh check|apply <side>` 分侧读取。`check` 不发送帧；
`apply --confirm-query-only` 仅发送固定 SDK 初始化已有的 `0x472`/`0x4AF` 查询，验证六轴角度
上下限、最大速度和最大加速度响应完整且结构有效。项目只记录非敏感参数，不记录设备序列号。

2026-09-15 已在 ROS、Piper 驱动和验收进程均未运行时完成左右查询。两侧结果一致：J1
`[-150°, 150°]`、J2 `[0°, 180°]`、J3 `[-170°, 0°]`、J4 `[-100°, 100°]`、J5
`[-70°, 70°]`、J6 `[-180°, 180°]`；六轴最大速度均为 `0.300 rad/s`，最大加速度均为
`0.500 rad/s²`。响应完整且通过结构检查，没有执行参数写入。

随后分别进行 5 秒被动 CAN 检查：左右各收到 15,200 帧，20/20 个预期反馈 ID 齐全，
未观察到控制/配置 ID、非预期帧或 CAN 总线错误。该窗口排除了当时存在持续并行命令源，
但没有控制帧时不能仅凭反馈确定机械臂的主/从角色。

## 厂商问题单

如需向 AGILEX 支持继续确认异常行为，提供以下非敏感证据：

1. 左右臂实际固件均为 `S-V1.8-2`，使用 0.6.1 SDK 和上述固定 Piper ROS commit。
2. 命令模式：CAN/MOVE J/位置-速度，速度比例 5%，J2 目标增量 `+0.005 rad`。
3. 结果：J2 相对基准超过 `0.020 rad`；J2 峰值 `0.205 rad/s`、`0.633 A`，J3 峰值
   `0.099 rad/s`、`0.962 A`；CAN 错误计数为 0。
4. 现场观察：发生移动，未观察到下砸、抖动、异响或其他异常。
5. 安全处置：software stop，机械支撑后 disable，随后关闭驱动。

要求厂商明确回答：

- 该固件应使用哪个 `piper_sdk` 与 Piper ROS 版本？
- 从主从/高跟随模式切换到位置-速度模式的完整安全恢复顺序是什么？是否需要断电重启？
- 发送 J2 小增量时 J3 电机运动是否符合设计；允许的关节跟随误差与瞬态超调是多少？
- 如何只读确认当前主臂/从臂角色，以及是否存在航空插头来源的并行控制帧？
- 对已经 software stop 的垂直安装/受重力机械臂，如何安全恢复并保持当前位置？

收到可核验答复或完成等效的只读诊断闭环前，不修改漂移/超调门限、不加入 J3 补偿、
不升级 SDK，也不再次运动。
